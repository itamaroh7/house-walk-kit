# מהיר ויפה: איך בית נשאר חלק במחשב נייד רגיל

הערכה מכוונת ל-60 פריימים בשנייה במחשב נייד עם Intel Iris Xe באיכות *מאוזנת*, ובמראה שקרוב לצילום. רוב היופי משולם פעם אחת, לפני הפריים הראשון (אפיית האור, טקסטורות דחוסות). רוב המהירות באה מזה שכל פריים זול **גם** לכרטיס הגרפי **וגם** למעבד. כאן מתוארים השיטה, המספרים והכללים לשמור על זה כשמוסיפים דברים.

## שני תקציבים, לא אחד

לכל פריים יש שתי עלויות:

- **כרטיס גרפי (GPU):** ציור הפיקסלים. הרזולוציה, ההצללה הרכה, הצללים, עלים שקופים וזיכרון הטקסטורות קובעים אותה. תפריט האיכות (מהירה / מאוזנת / גבוהה) והרזולוציה הדינמית עובדים כאן.
- **מעבד (CPU):** הכנת הפריים ב-JavaScript ובדפדפן לפני שהכרטיס מצייר משהו: מעבר על הסצנה, עדכון מטריצות, קריאת ציור לכל רשת בכל פריים, ניהול שיידרים. **שום הגדרת איכות לא נוגעת בזה.**

במחשב נייד, המעבד היה המגבלה. בית של 170 מ"ר עם 150 רהיטים עשה בערך 750 קריאות ציור, וצרך 20–25 ms של מעבד בכל פריים, בזמן שהכרטיס הגרפי סיים ב-9–11 ms. בגלל זה מבקר יכול היה לראות 40 פריימים בשנייה גם באיכות *מהירה*. התיקונים שלמטה חוצים את צד המעבד בחצי.

## קודם מודדים, בדפדפן אמיתי

- `npm run bench` (כשרץ `npm run dev`): פותח Chrome או Edge ברקע, עם הכרטיס הגרפי האמיתי ובלי תקרת 60 פריימים, ומריץ את הלולאה של הדף עצמו. מדפיס פריימים בשנייה, את הפריים באחוזון ה-90 ואת זמן הכרטיס הגרפי, בתוך הבית ומהרחוב.
- `npm run bench -- --compare`: ההאצות של המנוע דולקות וכבויות (`?fast=0`), לסירוגין, כדי שמחשב עמוס או חם לא יקבע את התוצאה.
- `npm run bench -- --profile`: לאן הולך זמן המעבד של פריים, פונקציה אחר פונקציה.
- בתוך הדף: `?gpumem` ו-`__gpuMemory()` (זיכרון הכרטיס לפי סוג), `__house.renderer.info.render` (קריאות ומשולשים), והתצוגה בפינה השמאלית העליונה (fps, זמן GPU, אחוז רזולוציה).

לא סומכים על זמנים מחלונית דפדפן מוסתרת או מטאב ברקע: הדפדפן מאט אותם, ואותו פריים נמדד בין 20 ל-40 ms. משווים אחד מול אחד (אותו מבט, אותה איכות, הרצות לסירוגין), ושומרים שינוי רק אם המספרים אומרים שהוא עוזר.

## מה המנוע עושה

משולם פעם אחת, לפני הפריים הראשון:

- **אפיית אור** במקום אורות חיים: האור של השמיים, השמש וכל מנורת תקרה נאפה לרשת של בדיקות בתוך הבית (`src/house/gi.js`) ונשמר עם התכנית (`public/gi`). החדרים מקבלים אור רך וחוזר במחיר של קריאת טקסטורה אחת.
- **טקסטורות דחוסות:** ‏KTX2 / Basis (`npm run compress`) נשארות דחוסות בכרטיס, בערך רבע מהזיכרון. טקסטורות זהות במודלים וברמות פירוט שונים משותפות, והעותקים הפתוחים משתחררים אחרי ההעלאה (`load-model.js`, `texture-memory.js`).
- **השתקפויות שנלכדות פעם אחת:** מראות ורהיטים מבריקים משקפים את החדר שלהם מצילום קובייה קטן בזמן הטעינה.

בכל פריים, בצד הכרטיס הגרפי:

- **מפת הצל של השמש מצוירת פעם אחת** (2048), ושוב רק כשדלת זזה. רהיטים בפנים לא מטילים צל שמש.
- **הצללה רכה (AO)** בעוצמה 2.5 בפנים (מעל 3 בערך היא מכתימה קירות), וכבויה באיכות *מהירה*.
- **רזולוציה דינמית** יורדת ל-80% (70% במהירה) כשהכרטיס עמוס, **והחלקת הקצוות (SMAA) תמיד דולקת** (בלעדיה התמונה נראתה מפוקסלת). חידוד קל בלבד.
- **רמות פירוט:** לכל מודל יש שלוש. רהיטים עוברים לרמה קלה מוקדם. רהיטים בעומק הבית לא מצוירים כשמסתכלים מבחוץ ממרחק של יותר מ-14 מ'. הדשא מוסתר כשנמצאים בפנים. עצים ושיחים מאוחדים לכמה רשתות בודדות.

בכל פריים, בצד המעבד (`src/engine/lib/batch-static.js`, `freeze-static.js`, `src/main.js`):

- **איחוד לפי חומר:** אחרי בניית הבית, כל רשת של כל מודל שעומד במקום נכנסת ל-`THREE.BatchedMesh` אחד לכל חומר. קודם מאחדים חומרים שמצוירים אותו דבר (פלדה, אלון, בד, שמגיעים בנפרד בכל קובץ מודל), וכך קריאת ציור אחת אוספת את המשטח הזה מכל המודלים. כל עותק עדיין בוחר רמת פירוט לפי מרחק. ‏~750 קריאות ציור ירדו ל-~230.
- **מטריצות מוקפאות:** הרנדרר מחשב מחדש את המטריצה של כל אובייקט בכל פריים. הבית לא זז, אז המטריצות שלו מחושבות פעם אחת, והרנדרר כבר לא עובר עליו. גם המטריצה של הסצנה עצמה מוקפאת (אחרת היא מסמנת כל אובייקט כ"השתנה" בכל פריים). רק כנפי הדלתות מתעדכנות, כשהן זזות.
- **מעבר אחד לזכוכית ולווילונות שקופים:** ‏three.js מצייר חומר שקוף דו-צדדי פעמיים ומסמן אותו כ"השתנה" לפני כל מעבר, ולכן השיידר שלו חושב מחדש לכל חלון, פעמיים בכל פריים. `forceSinglePass` נראה אותו דבר לזכוכית דקה ולבד.
- **חיתוך רק במבט מלמעלה:** מישורי החיתוך חושבו לכל קריאת ציור גם בזמן הליכה. עכשיו הם פעילים רק כשהמבט מלמעלה פעיל.
- **עקיפת באג ב-three.js r170:** הרנדרר שואל את ה-batch על `colorTexture`, אבל `BatchedMesh` שומר אותו בשם `_colorsTexture`. בגלל ש-`undefined !== null`, כל batch חישב מחדש את פרמטרי השיידר שלו בכל ציור. כל batch מגדיר `colorTexture = null`.

## מספרים (Intel Iris Xe, ‏1264 × 625, ‏Chrome)

| בית | איכות | מבט | לפני | אחרי |
|---|---|---|---|---|
| 170 מ"ר, 150 מודלים | מהירה | בפנים / מהרחוב | 41–45 / 39–43 fps | 80–97 / 80–94 fps |
| 170 מ"ר, 150 מודלים | מאוזנת | בפנים / מהרחוב | 42–48 / 41 fps | 84–95 / 73–83 fps |
| `example` | מאוזנת | בפנים / מהרחוב | 86 / 62 fps | 116 / 79 fps |
| `example-two-storey` | מהירה | בפנים / מהרחוב | 92 / 67 fps | 143 / 99 fps |

התמונה לא השתנתה: השוואת פיקסלים של אותו מבט לפני ואחרי שונה רק ברעש הגרעיני של "הסרט".

## כללים כשמוסיפים דברים

- רהיטים ואביזרים שעומדים במקום מאוחדים אוטומטית. כל דבר ש**זז או משתנה לכל עותק** אחרי הטעינה (כנף דלת, מנורה שנדלקת, עותק שצבעו משתנה בזמן ריצה) צריך לעבור דרך `skip` של `batchStatic`. אם הוא זז, מעדכנים אותו עם `object.updateMatrixWorld(true)` כשהוא משתנה (הבית המוקפא לא עושה את זה בשבילכם).
- לא קובעים `material.needsUpdate` ולא משנים `transparent`, `side` או `alphaTest` בכל פריים: כל שינוי כזה בונה מחדש את פרמטרי השיידר. משנים uniforms (צבע, שקיפות, עוצמה).
- לחומרים שקופים דו-צדדיים נותנים `forceSinglePass = true`.
- עדיף חומר אחד לכל משטח: חומרים זהים במודלים שונים מתאחדים לקריאה אחת, וחומרים שונים מעט (צבע או טקסטורה אחרים) הם קריאות נפרדות.
- בלי `onBeforeRender` לכל אובייקט ברשתות שעומדות במקום: זה משאיר אותן מחוץ לאיחוד.
- מריצים `npm run bench -- --compare` לפני ואחרי שינוי שעלול לעלות במהירות.

## עדיין איטי במחשב של מישהו?

- **תיבה אדומה שאומרת שהדפדפן מצייר בלי כרטיס המסך** (SwiftShader, ‏llvmpipe, ‏Basic Render): מפעילים האצת חומרה (בכרום: הגדרות ← מערכת ← "שימוש בהאצת גרפיקה כשאפשר") ומפעילים את הדפדפן מחדש.
- **`chrome://gpu`** צריך להציג "Hardware accelerated" ל-WebGL. במחשב נייד עם שני כרטיסים, אפשר בהגדרות של Windows (תצוגה ← גרפיקה) לתת לדפדפן את החזק מביניהם.
- **מחשבים ניידים** מאטים את הכרטיס הגרפי על סוללה וכשהם חמים: מחברים לחשמל.
- **מסך 4K או מסך צפוף** מכיל הרבה יותר פיקסלים: האיכות *המהירה* מציירת בגודל הפיקסלים של המסך עצמו.
- **`npm run bench` במחשב הזה** אומר איזה צד מגביל: אם זמן ה-GPU (בתצוגה) נמוך בהרבה מזמן הפריים, זה המעבד (סוגרים טאבים כבדים ותוספים). אם הם קרובים, זה הכרטיס הגרפי (מורידים איכות).
